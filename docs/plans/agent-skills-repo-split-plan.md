# Proposal: split agent skills into a Nix-driven repo

## Summary

This proposes moving the agent content out of dotfiles into a new public repo,
`prateek/agent-skills`, written entirely in Nix:

- **Moves:** skills, `AGENTS.md` and its convention docs, plugin policy, and the
  CLIs the skills call.
- **Build:** a flake builds every local plugin from pinned sources.
- **Activation:** a Home Manager module activates the plugins on each agent
  machine, building on upstream Home Manager's `programs.claude-code` and
  `programs.codex` modules.
- **Unchanged:** dotfiles keeps the machine configuration and stays on chezmoi.

Nothing here is decided. The choices below are the preferred options from
discussion on 2026-10-15, with the alternatives that were weighed. Accepting the
proposal would commit to several costly or hard-to-reverse steps, listed in "What
acceptance commits to". It should only move to `accepted` once the Phase 0 gates
have run.

## Why

- **The agent surface already behaves like its own project.**
  `agent-marketplace/` has its own justfile, uv lock, APM lock, tests, and a
  README written for consumers outside dotfiles. Most dotfiles churn in this area
  is agent content rather than machine configuration.
- **Most of the coupling is incidental.** The real seams are paths that assume
  one repo:
  - scripts 35, 36, and 39 and `work-overlay.tmpl` run and hash
    `{{ .chezmoi.sourceDir }}/../.agents/...`;
  - `agent_skill_lib.py` hard-codes `home/.chezmoidata/agent_plugins.toml`;
  - the skill console writes chezmoi templates in place.
- **Skill CLI dependencies aren't declared anywhere a tool can read.** About
  eleven CLIs sit in `clis.toml.tmpl` at `latest`, and the only link from a skill
  to its CLI is an inline comment. Enabling a plugin doesn't install its CLI, and
  disabling it doesn't remove one.
- **This lines up with the Nix target-state direction.** That research, on
  `origin/prateek/more-nix-research`, points to Nix composition with dendritic
  keyed modules. A small, bounded repo is a lower-risk first Nix deployment than
  migrating dotfiles itself, which the
  [migration assessment](../research/nix-migration-research.md) advised against.

## Proposed choices

| Axis | Proposed | Alternatives weighed |
| --- | --- | --- |
| Activation | Home Manager from the start, on every agent machine | The flake builds and chezmoi keeps activating, so machines without Nix still work. Or split first and add Nix later. |
| Boundary | Content moves; machine configuration stays (see "Boundary") | Move everything agent-shaped, including settings mergers, acpx, and CLI installs. Or move only the marketplace and `AGENTS.md`. |
| Language | Nix only, with no TOML policy or selection files and no Python | Keep the TOML policy, read with `builtins.fromTOML`, plus a Python build and reconciler that Nix calls. |
| Local plugin sources | Pinned `flake = false` inputs, dropping APM and the committed `apm_modules/` | Keep APM and the committed cache, and wrap the offline `apm pack` in Nix. |
| Official upstream plugins | Keep native marketplaces and self-updating, as ADR 0049 has it | Pin them as flake inputs, gaining rollback and losing auto-update. |
| Installation | Home Manager activation, using upstream client modules where they fit and tracking Home Manager master | A local reconciler run during activation, in Python or in bash generated by Nix. |
| Build library | Our own `modules/lib`, borrowing patterns from the [audit](../research/nix-agent-tooling-audit.md) | `agent-skills-nix` or `agent-plugins-nix` as an input. Rejected: neither emits both native manifests and catalogs, and the former's export rejects human-only skills. |
| Agent CLI packages | `numtide/llm-agents.nix` as an input without `nixpkgs.follows` | Package everything ourselves, or use its overlay, which misses the binary cache unless the nixpkgs revisions match. |
| Optional plugins | Additive profiles selected by a `.agent-profile` file in a repo | Isolated profiles in the style of quinnjr/claude-code-profiles, each with its own config dir. That splits login, history, and Orca hooks. |
| Skill CLI dependencies | Nix only, declared per skill | mise keeps installing them, from a file generated from skill declarations. Or they stay in dotfiles as they are today. |
| Module granularity | Mixed: one module per plugin, deps declared per skill, and modules for docs, clients, and upstream plugins | One module per skill, about 150 of them. Clients install whole plugins, so per-skill enablement would need plugins rebuilt per host. |
| Skill console | Replaced by a Nix-built report | Port the console to edit `.nix` source, or drop it entirely. |
| Visibility | Public, under the dotfiles audience rules (the employer appears only as DAYJOB) | Private. |

## What acceptance commits to

- **Installing Nix and standalone Home Manager on every agent machine,**
  including a Jamf-granted install on the work Mac.
- **Replacing whole subsystems.** APM acquisition and the committed cache go,
  superseding ADRs 0023 and 0025. So do the materializer, the reconcilers, and
  the skill console.
- **A new trust root.** Agent CLIs would come through numtide's binary cache and
  build infrastructure.
- **Home Manager master.** The features relied on landed in October 2026 and
  aren't in a release branch.
- **Two repos.** Some changes, such as adding an agent client, would need edits
  in both.

If the proposal is accepted, two ADRs would record it: one for the split with
Home Manager activation and profiles, and one for Nix acquisition and build,
superseding 0023/0025 and amending 0049 for the Codex-only adapters.

## Questions for review

1. Is Home Manager activation from the start worth the dependency on Nix
   reaching the work Mac? The alternative is to build with Nix and keep chezmoi
   activating until Nix is proven there.
2. Should Python be dropped entirely? The build port is modest (about 510 lines),
   but a reconciler or console written in shell is harder to keep correct. This
   proposal avoids needing either by leaning on Home Manager's client modules.
3. Is losing APM's import content scan acceptable, or should Phase 2 bring in a
   replacement scanner?
4. Is it acceptable to track Home Manager master and to carry workarounds for
   open issue #9906?
5. Does the per-repo profile approach cover how optional plugins (design, ios,
   pstack) actually get used?

## Boundary

**Would move to `agent-skills`:**

- `agent-marketplace/packages/`: authored skills, patches, and overlays. The
  `publish.toml` files and `plugin.json` manifests would be rewritten as
  `default.nix`.
- `home/dot_agents/`: `AGENTS.md`, `docs/`, and the `~/.claude/CLAUDE.md` link
  to it.
- Plugin policy: `agent_plugins.toml` and `agent_upstream_plugins.toml`,
  rewritten as Nix.
- The skill CLIs under "Agent skill backends" in
  `home/dot_config/mise/conf.d/clis.toml.tmpl`, with their env (`ASK_HOME`,
  `CRIT_NO_INTEGRATION_CHECK`).
- The jobs of scripts 35, 36, 37, and 39, which the Home Manager module would
  cover or make unnecessary.
- Agent docs: `references/agent-marketplace.md`, ADRs 0023/0025/0049, and the
  marketplace plans and research.

**Would be retired** rather than ported:

- `.agents/skills/agent-skill-management/`: the materializer, reconcilers,
  `codex_rpc.py`, `agent_skill_lib.py`, and the skill console.
- `agent-marketplace/scripts/`.
- APM.

A repo-local maintenance skill in the new repo would replace
`agent-skill-management`.

**Would stay in dotfiles:**

- Agent CLI installation: `agents.toml`, `agent_clis`, scripts 06/07, and the
  `features.tmpl` validation.
- The `modify_` mergers for Claude, Codex, Pi, and Cursor settings, minus the
  keys `agent-skills` would take over (see "Settings key ownership").
- acpx routing and harness data, the agent-session wiki sync, agentsview, Orca,
  crit config, and the zshenv agent variables.
- The work-overlay clone (`.chezmoiexternal`, script 36a).
- Repo-local skills for this checkout.

**Unresolved:** `home/dot_agents/bin/`, `lib/acpx/`, and `state/ios-triple.json`
currently materialize under `~/.agents/`. If Home Manager owns `~/.agents`, they
need a different target or a Home Manager entry.

## Proposed repo layout

```text
agent-skills/
├── flake.nix                  # inputs; outputs via flake-parts + import-tree
├── flake.lock
├── justfile                   # check, report, update-upstream, bump <pkg>
├── README.md
├── AGENTS.md                  # how to work in this repo
├── agents/
│   ├── AGENTS.md              # → ~/.agents/AGENTS.md (pointer section generated)
│   └── docs/*.md              # convention doc bodies
├── modules/                   # every file is a flake-parts module (dendritic)
│   ├── lib/                   # mkPlugin, mkSkill, catalog + manifest generators
│   ├── plugins/<name>.nix     # one per local plugin (17)
│   ├── upstream/<name>.nix    # one per official marketplace plugin
│   ├── docs/<name>.nix        # one per convention doc
│   ├── clients/               # claude.nix, codex.nix, pi.nix, omp.nix
│   ├── profiles.nix           # .agent-profile handling
│   ├── report.nix             # budget/inventory report
│   └── home-manager.nix       # homeManagerModules.default
├── plugins/<name>/            # payload sources: skills/, patches/, overlays/
├── pkgs/                      # CLIs missing from nixpkgs and llm-agents.nix
│   └── {acpx,ask,bird,shortcut-cli,rootly-cli,absurdctl,obsidian-wiki}.nix
├── tests/                     # nix checks: build, module (isolated home), wrapper
└── docs/                      # reference, ADRs, research
```

Flake inputs:

- `nixpkgs`, `home-manager`, `flake-parts`, `import-tree`, and `llm-agents`
  (numtide).
- One `flake = false` input per upstream source used by a local plugin. The URL
  scheme would be settled by gate 3.

Outputs:

- `packages.<system>.plugin-<name>`: one native plugin tree per plugin.
- `packages.<system>.marketplace`: an optional catalog for consumers without Nix.
- `packages.<system>.<cli>`: the locally packaged skill CLIs.
- `packages.<system>.report`.
- `homeManagerModules.default`.
- `checks`.
- `devShells.default`.

## Modules

A plugin module would declare content and metadata. The Codex and Claude
manifests would be generated from it with `builtins.toJSON`:

```nix
# modules/plugins/utils-agent.nix
{ inputs, self', system, ... }: {
  agent-skills.plugins.utils-agent = {
    version = "2.3.0";
    description = "Agent tooling skills";
    interface = { displayName = "Utils (agent)"; category = "Productivity"; };
    src = ../../plugins/utils-agent;                 # authored skills/, patches/, overlays/
    import.acpx-cli = { from = inputs.acpx; path = "skills/acpx"; };
    payloads = [ { from = inputs.acpx; path = "LICENSE"; target = "licenses/openclaw/acpx/LICENSE"; } ];
    skills = {
      ask         = { deps = [ self'.packages.ask ]; env.ASK_HOME = "$XDG_CACHE_HOME/ask"; };
      agent-slack.deps = [ inputs.llm-agents.packages.${system}.agent-slack ];
      acpx.deps        = [ self'.packages.acpx ];
      browser.deps     = [ inputs.llm-agents.packages.${system}.agent-browser ];
    };
  };
}
```

A doc module would pair a convention doc with its CLIs and the router line that
`AGENTS.md` shows for it:

```nix
# modules/docs/google-workspace.nix
{ pkgs, ... }: {
  agent-skills.docs.google-workspace = {
    source = ../../agents/docs/google-workspace.md;
    pointer = "Google Workspace or `gog`";
    deps = [ pkgs.gogcli ];
  };
}
```

`mkPlugin` would turn a declaration into a derivation, in this order:

1. Copy the selected input paths.
2. Apply patches in list order.
3. Copy overlays.
4. Optionally mirror invocation controls with `yq` in front-matter mode.
5. Write the generated manifests.
6. In `checkPhase`, enforce today's build rules: a `SKILL.md` in every skill
   root, no symlinks, paired human-only controls, and no paths escaping the
   plugin.

Checks on authored source would run at evaluation time. Checks on patched output
would run during the build, which avoids import-from-derivation.

## Host configuration and profiles

Hosts would enable modules by key:

```nix
programs.agent-skills = {
  enable = true;
  clients = [ "claude" "codex" "omp" "pi" ];
  plugins = [ "core" "review" "utils-agent" "mattpocock-codex" ];
  upstream = [ "last30days" "mattpocock-skills" "crit" "better-writing" ];
  docs = [ "engineering" "git" "mise" "google-workspace" /* … */ ];
  profiles = {
    ios    = [ "ios" "ios-tools" "apple-hig" ];
    design = [ "design" "ui-ux-pro-max" ];
    pstack = [ "pstack" ];
  };
  overlays = [ "/Users/prungta/code/work/…/agent-plugins" ];   # work overlay, runtime path
};
```

Proposed behaviour:

- **Claude base plugins.** Each would be a whole-directory `home.file` link at
  `~/.claude/skills/<name>`, which makes it a personal plugin (Claude Code
  2.1.157 and later).
  - This bypasses `programs.claude-code.plugins`. From 2.1.257, Home Manager's
    per-entry wrapper trips Claude's "path escapes plugin directory" check and
    silently drops manifest-declared components such as crit's hooks
    (home-manager #9906, open).
  - Switch back once that issue is fixed.
- **Codex base plugins.** These would go through `programs.codex.plugins`, which
  links them into `~/.codex/plugins/cache/home-manager/` and enables them. Each
  plugin derivation's `pname` and version must match its manifest.
- **Claude profile plugins** (preferred, pending gate 5).
  - They would be installed as personal plugins, defaulting to
    `enabledPlugins."<name>@skills-dir" = false` in user settings.
  - A repo's `.agent-profile` file would expand into `enabledPlugins` overrides
    in `.claude/settings.local.json`, which gets added to `.git/info/exclude`
    (harnix's pattern).
  - Unlike a wrapper, this would reach afable and Orca.
  - The only evidence so far is strings in the Claude binary.
- **Codex profile plugins.** Home Manager can't install a Codex plugin disabled.
  It always writes `enabled = true` and owns `~/.agents/plugins/marketplace.json`.
  - Profile plugins would therefore sit in a second local marketplace and never
    be installed.
  - A `codex` wrapper on `PATH` would walk up from `$PWD` to `.agent-profile` and
    add `-c 'plugins."<id>".enabled=true'`.
- **Fallback.** If those gates fail, Claude would use the same wrapper approach
  (`--plugin-dir <store path>`). afable runs the Agent SDK's vendored CLI, so it
  would miss profile plugins under a wrapper.
- **Skill deps.** The skill dependencies of enabled plugins, profile plugins
  included, would go into `home.packages`. A skill's `env` would become a
  `makeWrapper` around its CLI rather than a session variable, because
  chezmoi-managed zsh never sources `hm-session-vars.sh`.
- **Docs.** `~/.agents/docs/` would hold the enabled docs. `~/.agents/AGENTS.md`
  would be the authored body plus a "Convention pointers" section generated from
  the enabled doc modules.
- **Work overlay.** It needs runtime paths, so it can't be a store input. A small
  activation step would register it through the native CLIs, replacing script 39
  and the reconciler's `--overlay` mode. Slack doc composition (script 37) would
  move into the same step.

## Official upstream plugins

These would keep native marketplaces and self-updating:

- **Claude:** `extraKnownMarketplaces` and `enabledPlugins`, written through
  `programs.claude-code.mutableSettings`.
- **Codex:** it has no declarative way to add a GitHub marketplace, so an
  idempotent activation step would run `codex plugin marketplace add` and `codex
  plugin add` for anything missing.
- **OMP:** the same kind of step, once gate 5 confirms its CLI surface.
- **Updates:** `just update-upstream` would run the native update commands.
  Normal activation would only install missing plugins.

The Codex-only local adapters (mattpocock, better-writing, crit, ui-ux-pro-max)
would remain local plugins built from pinned inputs.

## Settings key ownership

Three writers would touch `~/.claude/settings.json` and `~/.codex/config.toml`:
the app, the dotfiles merger, and Home Manager's `mutableSettings` merge. That
only works with disjoint key ownership, and every writer must preserve keys it
doesn't own.

- **Home Manager would own** plugin and marketplace state:
  - `enabledPlugins` and `extraKnownMarketplaces`;
  - Codex `[plugins.*]` and marketplace entries;
  - `skillListingBudgetFraction`;
  - `~/.pi/agent/claude-plugins.json`, as a whole file.

  It would never declare `hooks` or `permissions`, because Home Manager replaces
  declared arrays and would drop the hooks Orca and Superset inject.
- **Dotfiles would keep** everything else. The plugin fragments
  (`agent-claude-plugin-settings.json.tmpl`, `agent-codex-plugin-config.toml.tmpl`,
  `work-overlay.tmpl`) would leave the merge inputs.
- **Stale keys.** Removing a declaration leaves its key in the file, so the
  module would keep a ledger of the keys it manages and delete any that drop out
  (as harnix and pr0d1r2 do).
- **GitHub marketplaces** would go only through `settings.extraKnownMarketplaces`.
  `programs.claude-code.marketplaces` overwrites that key, and it only emits local
  sources anyway.
- **Comments.** Home Manager's Codex merge drops comments, so the dotfiles
  `config.toml` template would lose its comments to avoid churn in `chezmoi diff`.
- **Don't set** `programs.pi-coding-agent.settings` (it would turn Pi's
  co-owned file into a store link) or `programs.codex.skills` (it would write
  through the chezmoi `~/.codex/skills` symlink).

## Report

`nix build .#report` would write Markdown and JSON from the built plugins:

- the skill-listing budget per client, in characters, for the base set and for
  each profile;
- the inventory of skills, with each one's source input and revision;
- human-only skills;
- skills whose deps are missing from the host closure.

`nix flake check` would fail when the base set exceeds the budget.

## Phases

### Phase 0: gates (before any decision)

These would produce the evidence the review needs. Record the results in a
dotfiles runbook.

1. **Nix on a personal Mac.** Install Nix and standalone Home Manager on
   personal-mbp or m4mini.
2. **Nix on the work Mac.**
   - The install needs a Jamf admin grant.
   - The daemon must trust the corp CA (`ssl-cert-file`).
   - Record how upgrades get sudo.
   - Configure numtide's cache as a trusted substituter.
3. **Fetch paths on the work Mac.** Test a `github:` input (codeload has timed
   out before), a `git+ssh://` input, the npm registry, and substitution from
   `cache.numtide.com`, e.g. `nix build --max-jobs 0` of `llm-agents#codex`.
   Without the cache, codex is a multi-GB Rust build.
4. **Cortex XDR.** Run `nix build` and `home-manager switch` on the work Mac
   with no process-group kill.
5. **Home Manager client modules,** in isolated `CLAUDE_CONFIG_DIR` and
   `CODEX_HOME` profiles:
   - Whole-directory `~/.claude/skills/<name>` links load as personal plugins,
     including crit's hooks (#9906).
   - `enabledPlugins."<name>@skills-dir" = false` in user settings can be
     overridden to `true` by a project's `.claude/settings.local.json`.
   - `programs.codex.plugins` plus `mutableSettings` coexists with the dotfiles
     tomlkit merger in both directions.
   - `codex -c 'plugins."<id>".enabled=true'` loads a plugin that's in a
     marketplace but not installed.
   - OMP and Pi can consume Home Manager-placed plugins. For OMP, the reference
     approach is wenjinnn's activation-time links into `~/.omp/skills`.

If gate 2, 3, or 4 fails, the proposal needs revisiting before acceptance: wait
on the work Mac, adopt the "flake builds, chezmoi activates" alternative there,
or reconsider.

### Phase 1: prepare dotfiles (no Nix)

- Partition the settings keys and remove the plugin fragments from the dotfiles
  merge inputs, proving with the config merge checks that each writer preserves
  the other's keys.
- Resolve the unresolved `~/.agents` boundary item.
- Freeze agent-content edits in dotfiles once Phase 2 starts.

### Phase 2: create the repo and port the build

- Extract with `git filter-repo`, keeping history for `agent-marketplace/packages`
  and `home/dot_agents`, renaming into the target layout, and dropping
  `apm_modules/` from history.
- Write `modules/lib`, one plugin module per package, and inputs pinned to the
  revisions in `apm.lock.yaml`.
- **Parity gate:** at the same upstream revisions, each `plugin-<name>` matches
  the last APM-built `plugins/<name>/` file for file, in bytes and modes, with
  semantically equal manifests.
- Settle what replaces APM's content scan.
- Package the seven missing CLIs under `pkgs/`, with `nix-update` scripts.
- Set up CI: `nix flake check` on macOS and Linux.

### Phase 3: Home Manager module, profiles, and report

- Write the client modules, profile handling, the overlay and upstream
  activation steps, and the report.
- Test the module in an isolated home on Linux CI, with stub CLIs. The
  native-client checks stay a local host lane.
- Add dotfiles' consumer flake under `nix/`, with `homeConfigurations.<hostname>`
  and a `hosts.nix`, plus a chezmoi script that runs `home-manager switch`. A
  dotfiles test would assert that each host's `clients` matches its
  `agent_clis`.

### Phase 4: cutover, one machine at a time

Order: m4mini, then personal-mbp, then the work Mac.

1. In dotfiles, delete the moved sources, the skill CLI lines in mise, and
   scripts 35, 36, 37, and 39. Run the first switch with `-b hm-backup`, because
   Home Manager refuses to overwrite files chezmoi left behind.
2. Uninstall the `prateek-local` plugins through the native CLIs, and clear
   their keys from settings.
3. Run `home-manager switch`. Verify the native plugin lists and
   `~/.claude/skills/`, check both Codex profiles (canonical and Orca
   `CODEX_HOME`), then restart sessions and reload Pi.
4. **Rollback:** activate the previous Home Manager generation, and revert the
   dotfiles cutover commit.

### Phase 5: cleanup

- Update the dotfiles `AGENTS.md` repo map, `tests/README.md`, `docs/index.md`,
  and the justfile.
- Archive this plan, and point `current_guidance` at the new repo's reference
  doc.

## Risks

- **Nix on the work Mac** is the long pole: the Jamf grant, sudo for upgrades,
  the corp CA, codeload, the npm registry, the binary cache, and Cortex.
- **Coupling to Home Manager master,** and to a workaround for #9906. Every
  bump would need gate 5's checks rerun.
- **Trust in numtide.** Its binary cache and build infrastructure would become a
  trust root for every agent CLI. The seven local packages would build locally,
  unless we add a cache or upstream `acpx`, `ask`, and `bird` to `llm-agents.nix`.
- **Three writers on co-owned settings.** A merger that drops unknown keys would
  silently undo the others.
- **Two install models.** Local plugins would be pinned and roll back with Home
  Manager generations; official plugins would self-update and not roll back.
- **Cross-repo edits** for changes that span CLI installation and agent content.
- **Pinned CLI bumps.** Every bump is a version and hash update. `nix-update`
  and `llm-agents.nix` would carry most of the work.
- **Losing the APM content scan** unless Phase 2 replaces it.
- **Per-skill deps are untested.** None of the audited configurations declares
  CLI dependencies per skill.
- **Sessions don't reload.** As today, a switch wouldn't refresh running
  sessions.
