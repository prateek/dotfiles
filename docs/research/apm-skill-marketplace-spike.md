# APM Skill Marketplace Spike

The [APM Agent Marketplace plan](../plans/apm-agent-marketplace-plan.md) turns
these findings into a proposed migration, including the activation and cache
behavior that this spike did not establish.
The [module-vendoring follow-up](apm-modules-vendoring-research.md) investigates
committing APM's fetched trees and using native acquisition; its new CLI
workflow is source-backed and remains unexecuted.

APM can replace the artifact-building part of our renderer if the reviewed
package directories become directly consumable plugins. Use APM to generate
manifests and marketplace catalogs beside those files. Its bundle exporter
does not preserve our complete payload.

This is one packaging tool with ten separate plugins from one source tree.
Two small static Codex manifests remain necessary to keep Claude hooks
disabled in Codex. Acquisition review, native installation, and enablement
remain separate responsibilities.

## Executed scope

Tested APM 0.29.1, Claude Code 2.1.143, and Codex CLI 0.153.4 on this Mac.
APM's release source is pinned at
[1b3d80ad2bfcb7ab3ce24bdac0538855aaddf3bc](https://github.com/microsoft/apm/tree/1b3d80ad2bfcb7ab3ce24bdac0538855aaddf3bc).

All candidate source copies, generated artifacts, probes, and agent state
lived in an OS temporary directory. APM and native consumer probes ran under
macOS `sandbox-exec` with `(deny network*)`; a curl control failed inside
that sandbox. Executables were called by absolute path with Mise shims
excluded from their environment.

Claude installed the temporary marketplace and all ten plugins into an
isolated `CLAUDE_CONFIG_DIR`. Codex's real app server read the marketplace
through `plugin/read` with an isolated `CODEX_HOME`. No model requests or
skill/helper/hook execution were used. These checks prove discovery and
packaging behavior, not that every skill's runtime dependencies are installed.

No production package, renderer, agent configuration, or live plugin
installation was changed. The disposable CLI installation and fixtures are
removed after validation; this report retains the commands and outcomes.

## Working source publication

The candidate made these one-time layout changes in temporary copies:

- Put each package's local and vendored skills directly under
  `skills/<skill-id>/`, preserving the contents and provenance files.
- Normalize the eight source filenames beginning with `literal_` to their
  intended runtime names.
- Move upstream acquisition declarations to `devDependencies.apm`.
- Omit `dependencies` entirely so `apm pack` emits a native manifest without
  building a bundle. An explicit `dependencies: {}` instead enables bundling.
- Remove `package.toml` from the publication fixture. APM reads its own
  metadata; machine enablement was not migrated into this fixture.

An illustrative publication root is:

```text
apm.yml
plugins/
  core/
    apm.yml
    apm.lock.yaml
    skills/<skill-id>/...
    .claude-plugin/plugin.json       generated by APM
  review/
    apm.yml
    skills/<skill-id>/...
    hooks/...
    evals/...
    .claude-plugin/plugin.json       generated by APM
    .codex-plugin/plugin.json        static hook override
  ...eight more plugins...
.claude-plugin/marketplace.json      generated by APM
.agents/plugins/marketplace.json     generated by APM
```

This is a publication layout, not a selected replacement location for the
repo's chezmoi source. A production migration must resolve source ownership
and filename materialization explicitly.

A package manifest can retain reviewed acquisition references:

```yaml
name: core
version: 1.0.0
description: Reviewed core skills
author: Prateek
targets: [claude]
devDependencies:
  apm:
    - forjd/better-writing
```

The real fixture retained each package's complete acquisition list and lockfile.
The source files, rather than a fresh upstream install, supply the publication.

The root declaration lists local plugin directories:

```yaml
name: prateek-local
version: 1.0.0
description: Reviewed local and vendored skills
marketplace:
  owner:
    name: Prateek
  outputs:
    claude: {}
    codex: {}
  packages:
    - name: core
      source: ./plugins/core
      category: Productivity
    - name: review
      source: ./plugins/review
      category: Productivity
```

The tested root contained all ten entries. It omitted entry versions: APM read
them from the local plugin metadata. Production commands would be a small
loop over the package directories running `apm pack --offline --force`,
followed by these root commands:

```sh
apm pack --offline
apm pack --offline --check-clean
```

Here `--force` refreshes APM-owned generated manifests when a package version
changes. Without it, APM preserves an existing native manifest. The root
catalog does not recursively build package manifests.
[Manifest producer](https://github.com/microsoft/apm/blob/1b3d80ad2bfcb7ab3ce24bdac0538855aaddf3bc/src/apm_cli/core/plugin_manifest.py),
[pack command](https://github.com/microsoft/apm/blob/1b3d80ad2bfcb7ab3ce24bdac0538855aaddf3bc/src/apm_cli/commands/pack.py).

## Native consumer and preservation results

| Guarantee | Executed result |
| --- | --- |
| Separate plugins from one local source | Both APM catalogs contained all ten packages with relative local sources. |
| No upstream fetch during publication or consumption | Manifest builds, catalog builds, Claude installation/update, and Codex reads passed with network access denied. |
| Payload preservation | All 1,471 source payload files matched after the documented path normalization, including their permission modes. |
| Provenance preservation | All 124 payload `SOURCE.md` files survived. |
| Human-only invocation contract | All 22 source skills with `disable-model-invocation: true` retained `policy.allow_implicit_invocation: false` in their OpenAI sidecar. This is file-contract validation. |
| Claude discovery | Native `plugin details` reported all 158 top-level skills across the ten installed plugins. |
| Codex discovery | Native `plugin/read` reported 162 skills, matching the existing renderer's per-plugin skill names exactly. |
| Claude hook discovery | The installed superpowers plugin reported its SessionStart hook. Supporting hook files remained present. |
| Codex hook suppression | Both review and superpowers returned zero hooks with their static Codex overrides, matching the existing renderer. |
| Repeatability | Repeated root generation produced identical JSON bytes; `--check-clean` passed. |
| Reviewed edit and release update | An edited vendored skill and a core version bump from 1.0.0 to 1.0.1 rebuilt offline. Claude's native update command reported the new version, and `plugin details` confirmed it. |

The Claude/Codex count difference is pre-existing. Codex also discovers four
nested `SKILL.md` files under `trycycle/subskills/`; Claude's inventory lists
the 158 top-level skills. A freshly generated baseline from our existing
renderer produced the same Codex skill and hook inventories as the candidate.

APM generates `.claude-plugin/plugin.json`, but has no native Codex manifest
producer. The installed Codex reader nevertheless accepts the generated Claude
manifest as a fallback. This runtime result corrects the stronger inference
that missing Codex manifest generation alone blocks this workflow.

That fallback also discovers Claude-shaped hooks. For review and superpowers,
the fixture therefore supplied:

```json
{
  "name": "review",
  "version": "1.0.0",
  "skills": "./skills/",
  "hooks": {}
}
```

These are native metadata files, not a second packaging tool. Their versions
need to track their packages. This spike did not reproduce the current
renderer's richer Codex display/interface metadata.

## Why the bundle route failed

The first experiment retained the existing nested local/vendor layout and used
`dependencies: {}`, development acquisition dependencies, and explicit
`includes`. Seven of ten packages packed immediately with identical skill
files. Further probes found these constraints:

| Input or output | Observed behavior |
| --- | --- |
| Existing iOS lockfile | Moving declarations to development dependencies alone did not exclude every entry; explicitly marking copied lock entries `is_dev: true` resolved the missing-deployed-files failure. |
| `includes: [hooks]` | Review failed on `hooks/SOURCE.md`; superpowers failed on `hooks/LICENSE.txt` because the explicit hook importer tried to parse those files as JSON. |
| `includes: auto` | Review and superpowers packed, but provenance/helper files under `hooks/` were absent from the bundle. Superpowers' emitted hook configuration still referenced the missing `hooks/run-hook.cmd`. |
| `includes: [skills, evals]` | Failed because the evaluation Markdown was not a recognized packable primitive. |
| Native manifest location | The bundle contained root `plugin.json`. Claude validation rejected that bundle directory for having no native manifest. The separately generated source manifest validated. |
| Source path transforms | APM preserved nested skill paths and `literal_` filenames. It did not perform our renderer's flattening or filename normalization. |

Thus successful `apm pack` output alone was insufficient evidence of a working
native plugin. Direct source publication avoids these bundle transformations
while keeping all reviewed supporting files.
[Bundle exporter](https://github.com/microsoft/apm/blob/1b3d80ad2bfcb7ab3ce24bdac0538855aaddf3bc/src/apm_cli/bundle/plugin_exporter.py).

## What this simplifies and what remains

APM can own the plugin-manifest and marketplace-catalog generation now done by
[render-agent-plugin-marketplace](https://github.com/prateek/dotfiles/blob/9a24d70664e52f119f00907929c2587305d54bc7/.agents/skills/agent-skill-management/scripts/render-agent-plugin-marketplace).
Native source directories remove its recurring skill-copy, flattening, and
payload-copy work after a deliberate source migration. A short build loop is
still needed because the catalog build does not build its children.

This does not replace the complete skill-management workflow. The vendoring
helper also preserves provenance, selects imported files, and accommodates
reviewed local changes. APM acquisition declarations and locks do not perform
that review. No new upstream import/update workflow was validated here.

Native installation and enablement also remain outside packaging. The existing
renderer emits agent configuration fragments, and the reconciler maintains
native install state. APM's generated Codex catalog used `AVAILABLE`, while our
existing catalog used `INSTALLED_BY_DEFAULT`. The six default-disabled packages
and current machine policy still need an explicit materialization/activation
owner. Codex cache refresh through native installation was not tested; Codex
validation used the native reader.

The spike supports APM as the sole packaging CLI, using direct source
publication and two static hook overrides. It does not justify deleting all
of the current tooling or adopting APM's bundle output unchanged.

## Mise setup incident

The initial APM 0.29.1 installation succeeded. An unnecessary second attempt
changed only `MISE_DATA_DIR` to a temporary directory while retaining global
configuration and the original Mise shims on `PATH`. That launch created
thousands of Mise descendants and exhausted macOS process slots.

The installed Mise 2026.6.14 source explains a matching recursion path:
`MISE_DATA_DIR` also changes the default recognized shims directory.
`is_mise_shims_dir` compares against the configured user/system directories,
so the inherited old user shims directory is no longer excluded. The npm
backend shells out to `npm view`; resolving that command through the old shim
re-enters Mise. An empty installation directory plus inherited `latest`
declarations supplies repeated version-resolution work.
[Environment defaults](https://github.com/jdx/mise/blob/v2026.6.14/src/env.rs#L109-L129),
[shim-directory predicate](https://github.com/jdx/mise/blob/v2026.6.14/src/file.rs#L874-L884),
[npm version lookup](https://github.com/jdx/mise/blob/v2026.6.14/src/backend/npm.rs#L232-L249).

The exact command environment and the large tagged process population were
observed; a complete spawning trace was not captured. Interrupting the parent
left descendants running. This is consistent with a documented
[related shim-recursion failure](https://github.com/jdx/mise/pull/10019),
but that upstream report uses a different directory mismatch.

A later process check showed zero Mise processes. The successful APM probes
used the already-installed executable directly, without another isolated Mise
installation. The setup failure provides no evidence against APM packaging.
